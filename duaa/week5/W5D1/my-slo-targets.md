# Service indicators and proposed targets

Team: Team 2

Use case: Content Tagging & Competency Mapping. The service supports analysis of learning content for tagging and competency/skill mapping.

Service measured: Baseline vLLM chat engine, team-serving endpoint (NodePort 30800), namespace team. Model: Qwen/Qwen2.5-1.5B-Instruct-AWQ.

Workload: Artificial chat workload generated by traffic.py: one caller for 60 seconds, a 30-second pause, then four callers for 60 seconds, with responses capped at 64 output tokens. The run completed 120 requests.

Measurement period: 2026-09-13T10:03:19+00:00 to 2026-09-13T10:06:19+00:00 (UTC).

Instrumentation gaps: Output quality and correctness for content tagging and competency mapping are not measured by these serving metrics. A separate task-quality evaluation is still required.

## SLI 1

Indicator: p95 time to first token (TTFT), measuring the 95th percentile latency before the first generated token is returned.

Panel: TTFT p95 (5m)

Unit: milliseconds

Target: <= 50 ms p95 TTFT. This is a provisional user-facing latency target based on the short lab workload.

Window: 5 minutes; the proposed SLO should be validated over a longer production-representative measurement window.

Observed: 39.000 ms p95 TTFT during the measured artificial lab workload.

Evidence: Team service Grafana dashboard, TTFT p95 (5m) panel, measured during the traffic.py run from 2026-09-13T10:03:19+00:00 to 2026-09-13T10:06:19+00:00 UTC. Query uses vllm:time_to_first_token_seconds_bucket with job="serving".

Why it fits: Time to first token directly affects how quickly a user perceives the service responding. Lower TTFT improves responsiveness for users submitting learning content for tagging and competency mapping.

Limitations: The observation comes from a short artificial workload with 120 requests. The target is provisional and should be retested over a longer period with representative content sizes, concurrency levels, and real project requests.

## SLI 2

Indicator: Completed requests per minute, counting requests that finish normally with stop or length completion reasons.

Panel: Completed requests / min (5m)

Unit: requests/min

Target: >= 20 requests/min during the tested workload. This is a provisional throughput target.

Window: 5 minutes; the proposed SLO should be validated over a longer production-representative measurement window.

Observed: Approximately 25 requests/min at the peak of the four-caller phase. After the workload ended, the value decreased as the five-minute rate window aged out the earlier requests.

Evidence: Team service Grafana dashboard, Completed requests / min (5m) panel and Completed requests over time panel, measured during the traffic.py run from 2026-09-13T10:03:19+00:00 to 2026-09-13T10:06:19+00:00 UTC. Query uses vllm:request_success_total with finished_reason matching stop or length.

Why it fits: Completed requests per minute measures whether the service can sustain useful request throughput while users submit learning content for analysis. It helps show whether the serving system can handle concurrent usage.

Limitations: Completed requests do not prove that the generated output is correct or meets the project's tagging and competency-mapping quality requirements. The measurement is based on a short artificial workload and should be repeated with representative requests and longer observation periods.
